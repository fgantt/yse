================================================================================
KEY FINDINGS: Why Shogi Engine NNUE Isn't Working
================================================================================

CRITICAL ISSUES (Prevent Convergence):
1. Weight initialization 256x too large [-128,128] vs Stockfish [-0.01, 0.01]
2. Output scaling arbitrary (/256) instead of proper quantization (/40)
3. Bootstrap problem: targets from same evaluation being trained
4. Missing proper TD(λ) implementation (no eligibility traces, wrong formula)

HIGH PRIORITY ISSUES (Performance & Accuracy):
5. Full accumulator refresh on every evaluation (no incremental updates)
6. No search integration (NNUE isolated from move ordering, TT)
7. Inconsistent scaling between training (tanh) and inference (linear)
8. Training configuration 10x too aggressive (learning rate 0.01 vs 0.001)

MEDIUM PRIORITY (Modernization):
9. No SCReLU or Quantmoid4 activation (only basic ReLU)
10. No output bucketing by piece count
11. Missing Shogi-specific optimizations (piece drops, captured pieces)

================================================================================
WHY STOCKFISH'S APPROACH WORKS
================================================================================

1. Quantization-First Philosophy
   - All design choices prioritize integer arithmetic
   - Weights, activations, and scaling carefully balanced for low-precision
   - No overflow, no precision loss from floating-point accumulation

2. Careful Initialization
   - Input weights small because sparse inputs accumulate slowly
   - Biases initialized near zero, learned gradually
   - Prevents initial saturation and enables learning

3. External Training Targets
   - Uses search evaluations or game outcomes as oracle
   - Not bootstrapped from weak evaluation
   - Gradual improvement: weak network → better search → better targets → stronger network

4. Aggressive Optimization
   - Lazy updates eliminate wasted computation
   - Incremental updates 10-100x faster than refresh
   - SIMD-friendly integer operations for 1M+ evals/sec

5. Continuous Improvement
   - 6+ years of refinement (HalfKP → HalfKA → HalfKAv2)
   - Modern additions: Quantmoid4, output bucketing, skip connections
   - Professional training pipelines with billions of positions

CONCLUSION
================================================================================

The current Shogi NNUE implementation is close to a working system but has
critical bugs that prevent it from improving engine strength:

1. Weight initialization is 256x too large (can't converge)
2. Output scaling is arbitrary (scores meaningless for search)
3. Training uses bootstrap targets (learns from itself, not external oracle)
4. No incremental updates (10-100x slower than necessary)
5. No search integration (NNUE isolated from engine)

GOOD NEWS:
- Fixes #1-#2 are trivial (change 2-3 lines)
- Fixes #1-#4 are sufficient to enable real improvement
- Foundation architecture is sound (256->32->1 matches Stockfish pattern)
- Most infrastructure already implemented (trainer, evaluator, integrations)

ACTION PLAN:
1. Fix weight init & output scaling (30 min each)
2. Re-train with fixed initialization
3. If still doesn't improve, fix training targets (2 hours)
4. Then optimize: incremental updates, SCReLU, output bucketing

The research shows NNUE is powerful but requires careful engineering.
Stockfish's approach is proven; the Shogi engine just needs to match it.
